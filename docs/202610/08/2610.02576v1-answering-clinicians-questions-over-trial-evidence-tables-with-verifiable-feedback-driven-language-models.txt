# Answering clinicians’ questions over trial evidence tables with verifiable, feedback-driven language models 

## Manan Roy Choudhury 1†, Suparno Roy Chowdhury 1†,Swastik Sahoo 1, Muhammad Ali Khan 2,Kaneez Zahra Rubab Khakwani 2, Mohamad Bassam Sonbol 2,Irbaz Bin Riaz 2* , Vivek Gupta 1*

Abstract 

Systematic reviews condense clinical trials into evidence tables, yet clinicians can interrogate these tables only through database queries, and many questions con-cern attributes that the table does not record, such as a drug’s target class or a harmonised endpoint. Here we introduce FD-SCoPE, a language-model frame-work that answers both kinds of question, exposes the query, the selected trials and the derivation rule behind every answer, and learns from expert corrections. On an oncology evidence table of 159 immune checkpoint inhibitor trial records, FD-SCoPE completed all 140 clinician-style tasks (alternatives, 90.7–97.9%). For questions needing derived attributes it retrieved 99.3% of relevant trial records at a positive predictive value of 89.8% and outperformed four alternative approaches (derived-value F1 77.7% versus 64.8–73.4%). Corrections on 299 questions, sim-ulated from reference answers, raised F1 on 1,201 unseen questions from 77.9% to 84.9%. Language models coupled with executable queries, verified programs and expert feedback can give clinicians auditable access to trial evidence. 

Keywords: clinical trials, evidence synthesis, large language models, text-to-SQL, human-in-the-loop, oncology

Clinical decisions and guidelines rest on evidence synthesised from trials, usually through systematic reviews, and trials are published faster than reviews can absorb them [1]. A review takes on average five experts and 67 weeks to complete [2], and what it produces is, in practice, a table with one row per trial, columns for disease, reg-imen, comparator, phase, enrolment, endpoints and follow-up. In a living review this table is updated as trials report [3], and it becomes the object that clinicians, guide-line panels and trialists return to with new questions. Which phase 3 trials tested a PD-1 inhibitor with chemotherapy? How many enrolled only PD-L1-positive patients? Which used a comparator other than chemotherapy? Each answer requires a database query or careful filtering of a spreadsheet, so most questions pass through an analyst. A second kind of question cannot be answered by a query at all. Reviewers often need attributes that are implied by a recorded value but not stored: the target class of an agent given its name, the platinum agent in a regimen, a follow-up duration grouped into clinically meaningful bands, or a free-text primary endpoint mapped to a standard category. These are re-derived by hand, question by question, and not always in the same way. Large language models (LLMs) have been applied to the earlier stages of evi-dence synthesis, namely search, screening, trial matching and data extraction, where exposing intermediate steps to experts improved both speed and quality [4–6]. For structured data, text-to-SQL methods translate questions into queries [7, 8]; decom-position, example selection and multi-agent refinement have improved their accuracy [9–11], and clinical work has addressed health-record querying, eligibility criteria and trial matching [12–14]. Three gaps remain for evidence tables. First, a fluent query is not necessarily the right cohort. Stored values carry aliases, abbreviations and incon-sistent spellings, and a dropped condition silently changes which trials are returned. Second, a query cannot produce an attribute that is not recorded, and systems that add model reasoning to tables either let the model choose the rows or write uncon-strained code [15–19]. Third, what an expert corrects is rarely kept in a form that later questions reuse, although stored feedback and cached model-written tools have improved language-model systems elsewhere without retraining [20, 21]. We therefore present FD-SCoPE, built to ask questions for clinical-trial evidence within tables in plain language for clinicians (Fig. 1), which integrates and extends on earlier FD-NL2SQL and SCoPE systems [22, 23]. A question is first screened for scope and then routed. A question about recorded fields is split into conditions that are matched to the table’s own values, compared with expert-approved examples and translated into a read-only query. A question about an unrecorded attribute uses the same steps to select the trials where in a planner states the derivation rule and the value is computed by a short program that has been checked against the model on sample rows, or row by row by the model when no program passes the check. Every step is recorded for inspection. Approved queries and corrected values are stored as examples and programs that later questions reuse. # 2 Results 

## 2.1 An oncology evidence table and three sets of questions 

We used the IOTOX living evidence table of immune checkpoint inhibitor trials in oncology, which holds 159 trial records and 32 fields covering identifiers, cancer type, agent and class, regimen, comparator, phase, line of treatment, enrolment, PD-L1 eligibility, endpoints and follow-up [22]. Three sets of questions were used (Table 1). The first holds 1,500 benchmark questions about recorded fields, each paired with a reference query and built from clinician-written templates. The second holds 1,500 questions that require an attribute not stored in the table, in 31 derivation families such as drug class, agents in a regimen, endpoint category and follow-up band [23]. The third holds 140 clinician-style tasks that we generated from the table to mirror how evidence is consulted: looking up facts for a named trial, counting trial publications for a disease, agent and phase, summarising the evidence landscape for a cancer type, and listing trials by enrolment, recency, biomarker restriction or comparator. Every system used the same open-weight model, Qwen3.8-27B [24]; Gemma-3-27B [25] was used to test dependence on the model. ## 2.2 FD-SCoPE completes clinician-style evidence tasks 

FD-SCoPE answered all 140 clinician-style tasks correctly (100%; 95% confidence interval (CI) 97.3–100; Fig. 2a). The seven alternatives answered between 127 and 137 (90.7–97.9%). Their errors fell mostly in the two commonest task types, fact look-up for a named trial and counts of trial publications (Fig. 2b), and had two main causes: a trial or drug name written in a form that differs from the stored one, so that no record matched, and a condition placed on the wrong field. FD-SCoPE avoids both by resolving every name against the values present in the table before the query is run. The 1,500 benchmark questions are harder, because each asks for a specific set of trials together with a specific set of fields. FD-SCoPE returned an exactly matching answer for 58.9% (95% CI 56.3–61.5), the highest of the eight systems (Fig. 2c). The best alternative, in the style of DAIL-SQL, reached 55.2%, a paired difference of 3.7 points (95% CI 1.9–5.5); few-shot and zero-shot prompting reached 49.3% and 49.9%. Agreement at the level of returned records was 67.4% execution F1 for FD-SCoPE and 67.1% for the DAIL-SQL style baseline, with the other systems between 45.6% and 63.3% (Fig. 2d). Every FD-SCoPE query was executable. With Gemma-3-27B, FD-SCoPE remained the most accurate at 46.8% exact match against 41.7% for few-shot prompting (paired difference 5.1 points, 95% CI 2.7–7.6; Fig. 2e), with similar execution F1 (58.5% and 59.4%; Supplementary Table S1).

## 2.4 Expert corrections become reusable rules 

We next asked whether corrections to a sample of answers carry over to new questions. From these the system wrote and validated 24 derivation programs and stored 72 approved trial-selection queries. # 3 Discussion 

A curated trial table is one of the most reused products of evidence synthesis, yet it is usually consulted through an analyst or by hand. FD-SCoPE lets a clinician ask such a table questions in plain language and see how each answer was reached. In this evaluation it completed every clinician-style task, found nearly all relevant trials for questions about unrecorded attributes while keeping false inclusions near one in ten, derived those attributes more accurately than four alternative approaches using the same language model, and improved after corrections to a fifth of the questions. The design choice that mattered most was to let a query, rather than the model, decide which trials an answer covers. When the model read the table and chose the 9rows, about one relevant trial record in ten was missed and fewer than half of the answers covered exactly the right trials; replacing query-based selection within FD-SCoPE itself lowered its accuracy by ten points. For evidence work this is the more consequential error. A wrongly derived label is visible next to its source value and can be corrected, whereas a trial that is silently missing from an answer cannot be seen. Because selection and derivation are separate steps, a reviewer can also tell which of the two failed. The second choice was to turn corrections into rules. In a living review the same concepts recur as trials are added: target classes, regimen backbones, endpoint cate-gories. A correction that only fixes one answer is spent once, whereas a validated rule applies to every later question of that family and to trials that were not part of the correction, as the gain on unseen trials shows. The one family that deteriorated after feedback shows the other side of reuse: a rule applied outside the family it was learned for can be confidently wrong. We therefore regard expert approval of learned rules, with their validation record in view, as a required step rather than an option. This is in line with experience from earlier stages of evidence synthesis, where language models were most useful when experts could inspect and edit intermediate outputs [4]. FD-SCoPE is complementary to systems that search, screen and extract trial data from publications [4]: those build the table, and FD-SCoPE makes it answer-able once it exists. Its components draw on established text-to-SQL ideas, namely decomposition, example retrieval, and validity and execution checks [9–11, 28], and on program-aided reasoning [18, 19]. What it adds is grounding of every condition in the values the table actually holds, selection of trials by query before any derivation, and retention of reviewed work. On recorded-field questions its advantage over the strongest text-to-SQL baseline was modest and confined to complete, exactly match-ing answers, and it used about twice as many tokens per question (Supplementary Table S1). The larger differences were on derived attributes and on tasks about named trials and drugs, where matching names to stored values decides whether any record is found. This study has limitations. First, it concerns a single oncology table of 159 trial records; multi-table registries with joins and larger schemas may behave differently. Second, no clinician used the system in this study. The clinician-style tasks were gen-erated by the authors from templates, and feedback was simulated from reference answers, so the results show that corrections can be retained and transferred, not how much expert effort they cost. Third, the benchmark questions were expanded from clinician-written templates by programmatic variation and phrased by a language model; any residual mismatch between a question and its reference query lowers the attainable score for every system, and exact-match accuracy on recorded-field ques-tions was below 60% for all of them. Fourth, FD-SCoPE was developed with access to these benchmarks, while the alternative methods are our re-implementations for a single-table setting and were not tuned in the same way. Fifth, each system was run once, so the intervals reflect sampling of questions and not run-to-run variation. Finally, performance depended on the language model, typing errors in clinical terms reduced accuracy, and the safety prompts were written alongside the scope check, so that result is a functional check rather than an estimate of real-world safety. 10 The next step is a prospective study in which reviewers of a living evidence resource pose their own questions, inspect the recorded steps and approve or reject learned rules, with time and agreement as outcomes and with structured human evaluation of the kind proposed for healthcare language models [29]. Extension to multi-table trial registries, ontology-based normalisation of drug and disease names [30, 31], and calibrated abstention when a question cannot be answered from the table [32, 33] are natural technical priorities. FD-SCoPE is not a decision-making system; it is an interface to evidence that experts have already curated. Free-text answers from language models can remain inaccurate or potentially harmful even when grounded in retrieved clinical guidelines [34]. Our results indicate that language models are most dependable for this purpose when they formulate the question, exact tools compute the answer, and what experts correct is kept. 

# 4 Methods 

## 4.1 Study design and evaluation framework 

We conducted a retrospective computational evaluation of FD–SCoPE as a natural-language interface to structured oncology clinical-trial evidence. The unit of evaluation was a question, and the intended output was a table containing the relevant trial records and requested information. Questions could require either direct retrieval of values already recorded in the table or derivation of an attribute that was not explicitly stored. We defined derivation as the application of a clinical or analytical rule to recorded information to produce a new value. For example, when a record identified nivolumab as the immune-checkpoint inhibitor but did not explicitly state its target class, the system derived the value PD-1 from the recorded drug name. Performance was assessed at three levels. First, trial identification measured whether the system selected the appropriate clinical-trial records; for example, a ques-tion concerning small-cell lung cancer trials evaluating nivolumab should retrieve those trials without including studies of other cancer types or agents. Second, evidence-table accuracy measured whether the returned table contained the expected records and requested fields; for example, the National Clinical Trial identifier, PubMed identifier, trial name and treatment information should agree with the reference table for every returned trial. Third, derived-attribute accuracy measured whether values inferred from the retrieved records were correct; for example, nivolumab, atezolizumab and ipilimumab should be classified as PD-1, PD-L1 and CTLA-4 inhibitors, respectively. 

## 4.2 Clinical-trial evidence source 

The source was a read-only SQLite database with one table of 159 trial records and 32 fields from the IOTOX living evidence resource on immune checkpoint inhibitors in oncology [22]. Fields describe trial identity and publication history, cancer type, agent and immune-checkpoint-inhibitor class, regimen and comparator, phase, number of arms, line and setting of treatment, enrolment, biomarker-based eligibility, endpoints 11 and follow-up. Field names and values were used exactly as stored, including abbrevi-ations, alternative disease labels and variant spellings, so that the evaluation reflects the terminology met when searching structured evidence. 

## 4.3 Clinician-guided question development 

Participating clinicians developed the initial question templates and exemplar ques-tions to represent information needs that arise when reviewing oncology trial evidence, covering diseases, therapeutic agents, treatment classes, comparators, biomarkers, trial design and outcomes. They reviewed the templates and exemplars for clinical rel-evance, clarity and consistency with the evidence table. The approved templates and exemplars were then used to produce the question sets by varying concepts, constraints and requested outputs [22, 23]. 

## 4.4 Question sets and data partitions 

Recorded fields. The benchmark holds 1,500 questions with executable reference queries. Each clinician-approved question and query was changed by one program-matic edit of the output fields or the conditions, retained if the query executed and returned records, and phrased as a natural-language question by a language model [22]. A fixed random subset of 300 questions was used for component analysis and robustness testing. The example bank held 200 expert question–query pairs and their condition-level sub-questions (987 retrievable entries). Benchmark questions and banked examples derive from the same pool of expert queries, so some share con-ditions; every example-based system (FD-SCoPE, the DAIL-SQL style baseline and few-shot prompting) drew on this bank. 

Derived attributes. The 1,500 questions span 31 derivation families, including treatment-class mapping, interpretation of combination regimens, identification of anti-VEGF and tyrosine-kinase-inhibitor agents, categorisation of trial size, phase and publication period, endpoint classification and construction of PubMed links [23]. Reference values were generated by independently specified derivation functions that were never available to any evaluated system. Fields that directly reveal the target value were hidden. Seventy-one questions had no matching trial records; an empty answer was considered correct for these. A 304-question subset was used for component analysis. 

Clinician-style tasks. We generated tasks from the table with templates for six task types (Fig. 2b), each with a reference query. A development set (random seed 7) was used while building the system; the 140 tasks reported here were generated afterwards with a different seed (11). Look-up, count and landscape tasks were scored by exact agreement of the result, and listing tasks by exact agreement of the set of trial records. 

## 4.5 FD-SCoPE architecture 

FD-SCoPE combines guarded retrieval of trial records with row-level derivation of attributes that the table does not hold (Fig. 1). It comprises a scope and safety gate, a question router, a schema and value catalogue, a decomposition module, an exemplar retriever, an SQL generator, an execution guard, a derivation planner and 12 two feedback-updated banks. The scope gate uses pattern rules to decline requests to modify data, instructions to ignore the system’s rules, requests for clinical advice and requests for patient-level data. A rule-based router decides whether the requested output is recorded or must be derived. In the benchmark evaluations the pathway was fixed by the question set, so that routing errors were not conflated with retrieval or derivation accuracy. 

4.5.1 Clinical concept grounding and exemplar retrieval 

At initialisation, FD-SCoPE builds a catalogue from the database schema and the observed values of every field. Question phrases are resolved against it by exact agree-ment, normalisation of case and whitespace, predefined aliases and, last, approximate string matching (minimum similarity 0.72 for fields and 0.86 for values). Approxi-mate matching is disabled for identifiers and trial names, because a single-character difference can identify a different study. Each question is decomposed into at most six atomic clinical constraints, such as cancer type, agent, treatment class, biomarker requirement, phase, comparator, year or number of arms. Deterministic extraction rules are combined with a model-generated decomposition, and each constraint is grounded to a field, a comparison operator and a stored value. For each constraint the three most similar entries of the exemplar bank are retrieved by cosine similarity of all-MiniLM-L6-v2 sentence embeddings [35, 36], with a bonus of 0.15 for exemplars that share a grounded field or value, and three more are retrieved for the whole question, following evidence that semantically similar demonstrations improve in-context learning [37]. Retrieved exam-ples serve as structural guidance; the question and its grounded constraints remain authoritative. 

4.5.2 SQL generation and guarded execution 

FD–SCoPE translates each clinical question into a single read-only SQLite query using the available database fields, stored clinical terminology and relevant clinician-approved examples. For instance, if there is a question asking for renal-cell carcinoma trials, evaluating nivolumab is translated into filters for the disease and treatment fields, with trial identifiers and relevant study information included in the returned table. When the requested output is not explicitly stated, the system selects clinically informative fields based on similar validated examples. Before execution, each query is checked to ensure that it uses valid fields and termi-nology, accesses only the clinical-trial evidence table and cannot alter the underlying data. If an otherwise valid query fails, the model is allowed one revision attempt. Queries that return no matching trials are not automatically broadened, thereby preserving the clinical criteria specified in the original question. 

4.5.3 Hybrid retrieval and derivation 

For questions about unrecorded attributes, the SQL pathway first selects the trial cohort, and the selection query is extended to return the source field and trial iden-tifiers. A planner receives the question and up to eight selected rows and returns the 13 source field, the derivation rule, the answer type and, optionally, a Python expression that implements the rule. Derivation follows a three-stage hierarchy. A stored pro-gram for the same derivation family and source field is used if one exists. Otherwise a proposed program is accepted when it agrees with the model on at least 85% of up to six sampled rows; it is then applied to the whole cohort and stored. If no program is accepted, the model derives the value for each row in batches of at most 40. Pro-grams are single expressions run in a sandbox without imports, file access, unrestricted built-ins or private attributes, and a validation or execution failure causes reversion to row-level derivation. Derived values are normalised to the expected answer type and appended to the retrieved trial records. 

## 4.6 Clinician feedback and feedback-driven learning 

The feedback interface allows a clinician or other domain expert to review an answer table, approve correct outputs and supply corrected values or derivation rules (Fig. 1). An approved question–query pair is added to the exemplar bank. Corrected derived values are grouped by derivation family and source field, with repeated source values collapsed. The model is asked to write a program that reproduces them. When there are at least six distinct values that are available, 30% are withheld for validation, and a program is accepted only if it agrees with at least 90% of both the fitting and the validation values without execution errors, with up to four attempts. For look-up families that cannot be validated on unseen values, a program fitted to all values is accepted at 95% agreement. Accepted programs enter the program bank marked as approved. For the controlled feedback experiment, the derived-attribute questions were split within each derivation family by a seeded random split (seed 42), with 20% assigned to feedback (299 questions) and the remainder held out (1,201 questions). Reference answers of the feedback questions were supplied through the learning mechanism in place of expert corrections, which gave a consistent signal while keeping the reference answers of held-out questions unavailable to the system. Both banks were frozen before the held-out questions were answered. A second condition restricted program learning to a deterministic half of the trial registry identifiers and measured accuracy on values from the other half. 

## 4.7 Prompt design 

FD-SCoPE uses stage-specific prompts for the components shown in Fig. 1: question routing, decomposition, SQL synthesis, SQL repair, fallback row selection, derivation planning, row-level derivation, SQL back-translation and derivation-program induc-tion. Each prompt has a system instruction that defines the responsibility of the stage and a user message with labelled input blocks, and responses are constrained to JSON or another defined machine-readable format. In the reported experiments the routing and back-translation prompts were not exercised, because the pathway was fixed by the question set and no example augmentation was used; no query needed 14 model repair; and fallback row selection was used for four derived-attribute ques-tions and in the component analysis. Complete prompt templates are provided in the Supplementary Methods. 

## 4.8 Alternative approaches 

All comparison systems used the same language model, clinical-trial evidence table, read-only database and evaluation procedure. Generation used a temperature of 0, except for the C3-style baseline, which required stochastic sampling at a temperature of 0.7. The comparison systems did not have access to FD–SCoPE’s decomposition outputs, clinician-approved exemplar bank, output-field completion or guarded repair process. We first evaluated three prompting baselines. Zero-shot prompting provided the database structure, examples of the terminology stored in each field and the clini-cal question. Few-shot prompting additionally included four fixed clinician-approved question–SQL demonstrations [38]. Chain-of-thought prompting guided the model through interpretation of the clinical question, identification of relevant fields and con-struction of the query. It included one successful and one unsuccessful worked example [39]. We also implemented four natural-language-to-SQL approaches adapted from published methods. The DIN-SQL-style baseline identified relevant database fields, estimated question difficulty, generated a query and reviewed it for errors [9]. The DAIL-SQL-style baseline selected eight demonstrations according to question simi-larity after masking literal clinical values [10]. The C3-style baseline generated ten candidate queries and selected the result produced most consistently across the can-didates [26, 40, 41]. The MAC-SQL-style baseline divided the task among selector, decomposer and refiner roles, with a maximum of three refinement rounds [11]. These implementations were written for the present single-table setting and followed the principal workflow of each published design. Separate comparisons were used for questions requiring derived attributes. The BlendSQL-style baseline identified the relevant records and asked the model to derive an answer for each distinct source value [16]. The code-agent baseline generated and, when necessary, revised pandas code that was executed in a restricted environment [17]. The row-retrieval baseline answered from the 40 records most similar to the question. The whole-table baseline supplied the complete evidence table directly to the model. Full settings are provided in Supplementary Table S14. For Gemma-3-27B-it, we evaluated FD–SCoPE together with the zero-shot and few-shot prompting baselines. The remaining method baselines were evaluated only with the primary model. 

## 4.9 Component analysis, robustness and safety 

Components were removed one at a time with all other settings fixed and an indepen-dent, empty learning state for every run. For derived attributes we removed program induction and the program bank, removed the planner, removed output normalisation, or replaced query-based selection with selection by the model over the whole table. 15 For recorded fields we removed catalogue grounding, exemplar retrieval, output-field completion or model-based decomposition, and varied the share of the exemplar bank that was available. Robustness was evaluated by applying meaning-preserving rewrites to eligible held-out questions while keeping the reference query [42]: conversion to lower case, a brand name in place of a generic treatment name, a disease abbreviation, immune-checkpoint-class shorthand, or one typing error in a clinically relevant term. Only questions to which a rewrite applied were included in that comparison. The safety set contained 46 prompts: 12 requests to modify the database, 10 prompt-injection attempts [43], eight requests for clinical advice, six requests for patient-level information and 10 appropriate read-only controls. It was run with the scope gate and the guard both enabled, and with the scope gate disabled, which sep-arates the ability to decline an inappropriate request from the ability to prevent an unsafe database operation. A hash of the database was compared before and after each run. 

## 4.10 Outcome measures 

For recorded-field questions, predicted and reference queries were executed on the same database. Execution exact match required the reference result to be reproduced; additional context fields were permitted when all expected fields and values were present. Execution F1 summarises row-level precision and recall after alignment of corresponding fields. For derived-attribute questions, rows were aligned on trial reg-istry identifier, PubMed identifier, trial name and source value. Derived-value F1 was computed after normalising case, whitespace and equivalent label forms, and also in exact form; we further report the share of questions with every derived value correct, the F1 and exact agreement of the whole evidence table, and the accuracy of individ-ual derived values. An empty answer to a question with an empty reference table was counted as correct. Trial-level sensitivity and positive predictive value compare the set of trial records in an answer with the reference set, and the exact trial set is the share of questions for which the two sets are identical. Token use is the sum of prompt and completion tokens over all model stages divided by the number of questions. 

## 4.11 Statistical analysis 

Measures were computed for each question and averaged. Confidence intervals are 95% percentile intervals from 1,000 non-parametric bootstrap resamples [44] of questions (NumPy random seed 0); for clinician-style tasks we report Wilson intervals [45]. Differences between two systems on the same questions are reported with paired bootstrap intervals from 10,000 resamples (Supplementary Table S11). No hypothesis tests were performed. Each system was run once, so the intervals represent sampling variability across questions rather than variability across repeated runs. 

## 4.12 Models and computational environment 

The primary experiments used Qwen3.8-27B with thinking mode disabled, and Gemma-3-27B-it was used for the model comparison. Models were served with vLLM 16 0.27.1 [46] through an OpenAI-compatible interface on NVIDIA H200 graphics pro-cessing units in bfloat16 precision, with decoding temperature 0.0 and top-p 1.0; the sampling step of the C3 style baseline was the only exception. Served context limits were 40,000 tokens for Qwen3.8-27B and 24,000 tokens for Gemma-3-27B-it (Sup-plementary Table S13). Orchestration, database execution, sentence embedding and evaluation ran on central processing units under Python 3.12. Model responses were cached with a key comprising the model identifier, the complete prompt, the decoding parameters and the response schema, and cached responses were included in token accounting. 

## 4.13 Reproducibility and software verification 

Every run retained its resolved configuration, per-question predictions, token-usage summary and evaluation report, and FD-SCoPE runs additionally stored a structured trace of the selected pathway, grounded constraints, retrieved exemplars, generated SQL, execution results and derivation method for every question. Random seeds were recorded for data partitioning, feedback experiments, bootstrap resampling and rewrites. The software has 21 deterministic offline tests covering catalogue con-struction, grounding, routing, SQL safety, query repair, hybrid selection, program sandboxing, feedback and end-to-end evaluation, all of which passed in the evaluated code state. Model identity, decoding settings, prompts and uncertainty are reported with reference to the TRIPOD-LLM guideline [47].
